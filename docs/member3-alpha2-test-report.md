## 1. 测试范围

本次测试覆盖：

- 标签分类查询、创建、修改和删除；
- 分类名称大小写不敏感唯一；
- 标签查询、创建、修改和删除；
- 同一分类内标签名称唯一，允许跨分类同名；
- 条目标签关系创建、查询和删除；
- 条目新增标签时评分可为空；
- 条目标签评分范围为 1 至 10 的严格整数；
- 整数字段拒绝 0、11、9.5 和布尔值；
- 删除被引用标签、非空分类和系统分类时返回冲突；
- 同一 `(entry_id, tag_id)` 的幂等更新；
- 请求成功提交和异常回滚的事务边界。

本次测试不覆盖：

- 前端当前使用 Mock 数据时的完整用户界面；
- 分享包的导出、预览和导入；
- 桌面安装包的最终验收。

## 4. 典型用户场景

### 场景：为条目设置多个标签和评分

1. 创建标签分类“内容题材”。
2. 在分类中创建“科幻”和“剧情”两个标签。
3. 创建条目并关联两个标签。
4. 将“科幻”设为 9 分，“剧情”暂不评分。
5. 查询条目标签，确认两个标签和评分都正确保存。
6. 将“科幻”改为 10 分，再清空评分。
7. 尝试评分 0、11、9.5，预期返回 422。
8. 尝试在相同分类创建重名标签，预期返回 409。
9. 尝试删除仍被引用的标签，预期返回 409。

实际结果：

- 后端 API 场景通过。
- 前端完整交互场景无法执行，原因是前端尚未切换真实接口，仍使用 Mock 和旧评分结构。

## 8. 习得的软工原理、方法与技能

### 原理

- 契约先行：先冻结字段、接口和错误码，再并行实现前后端。
- 单一事实来源：标签评分范围统一以 `docs/tag-rating-contract.md` 为准。
- 职责分离：领域模型负责格式约束，应用服务负责业务规则，仓储负责数据访问。
- 幂等性：同一标签关系使用 `PUT` 重复写入不会产生重复数据。
- 可追踪性：需求、实现、测试和交付记录通过 Issue、PR 与提交串联。

### 方法

- 使用测试驱动开发，先运行失败测试，再补最小实现。
- 使用边界值分析覆盖 `null`、1、10、0、11、9.5 和布尔值。
- 使用分层测试覆盖领域、服务、HTTP 和事务边界。
- 通过跨成员 Issue 明确依赖、责任和未完成项。

### 技能

- FastAPI、Pydantic、SQLAlchemy 和 SQLite；
- pytest 自动化测试与错误输出分析；
- Git 分支、提交、推送和 Pull Request；
- Markdown 契约、交接文档和测试报告编写；
- 跨模块接口核对和风险说明。
