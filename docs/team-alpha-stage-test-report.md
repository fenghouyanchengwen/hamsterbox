## 1. 摘要

Alpha 第一阶段已经建立持续集成、Windows 每日预览构建和桌面启动链路。Alpha 第二阶段完成条目、资源、标签、评分、检索、内置适配器、安装程序和部分桥接边界的实现与测试。当前自动化基线为：

```text
161 passed, 1 xfailed, 111 warnings
```

该结果说明主线大部分已实现模块可以稳定回归，但唯一严格预期失败对应真实缺陷：`build_registry()` 重复注册 `FallbackAdapter`，导致适配器注册表无法构建。成员五分享包独立分支另有 `214 passed, 1 xfailed`，其中专项 53 项通过；这些结果不能替代 Windows 桌面和跨设备场景验收。

团队 Alpha 出口尚未完全达到。主要缺口是：

- 适配器注册表自动化用例失败；
- 条目列表仍返回本地 `cover_path`，存在隐私风险；
- 时间响应缺少 UTC 时区；
- 前端仍默认使用 Mock，且字段名、评分接口与真实后端不一致；
- Entry API 尚未接入 `review` 和 `lifecycle_state`；
- 桌面启动器未挂载 `js_api`，原生文件选择与打开链路未验收；
- 前端没有自动化行为测试，交互场景只有静态走查；
- 分享包导出和只读预览已有函数级自动化证据，但界面、正式导入、冲突处理和跨设备场景未完成；
- Windows 安装已在 3 台设备完成，但三台设备使用相同 Windows 版本；TC-06 至 TC-08 没有独立手工记录。

## 3. 测试方法

团队采用分层测试与场景测试相结合的方式：

1. 领域层验证数据类型、边界和业务规则。
2. 应用层验证服务编排、事务和错误映射。
3. 仓储层验证 SQLite 查询、迁移、约束和级联。
4. HTTP 层验证参数、状态码、错误码和响应结构。
5. 端到端测试验证资源失效、恢复和重新检测工作流。
6. 桌面与发布链路验证打包、启动、安装和卸载。

测试结论分为三类：

- **自动化通过**：有命令、断言和可重复结果。
- **手工记录**：由成员实际操作并提交结果，但没有完整自动化证据。
- **未执行**：没有实际结果，不推断为通过或失败。

| ALPHA-14 | `source_library_id` 的生成与持久化未确认 | 高，影响稳定来源识别 | 待确认 | 分享包与数据 |

### ALPHA-01 适配器重复注册

`TypeRegistry` 当前拒绝同类型适配器重复注册。多个 `FallbackAdapter` 分别承载游戏和三维模型扩展名，这是合法用法，但注册表把“同类型”误当成“同一注册项”。严格 `xfail` 使用 `--runxfail` 执行时会稳定抛出 `ValueError`。

修复需要调整注册表的重复判断语义，或把扩展名映射与适配器实例生命周期分离。修复后必须移除 `xfail` 并重跑全部适配器测试。

### ALPHA-02 列表泄露本地路径

检索列表项继承 `EntryRead`，直接序列化 `cover_path`。接口契约要求该字段仅供后端使用。当前响应会把用户本地目录结构暴露给前端或分享截图。

列表应使用独立响应模型，将封面转换为受控标识或相对引用。封面是本地绝对路径这一事实不应进入列表 API。

### ALPHA-03 时间缺少时区

SQLite 读回的无时区时间直接序列化，响应不带 `Z` 或 `+00:00`。浏览器按本地时间解释后，UTC 时间在北京时区显示偏移八小时。应在统一响应模型中补齐 UTC 时区并增加接口断言。

### ALPHA-04 与 ALPHA-05 前端联调

前端类型使用 `cover`、`summary`、`exists`，后端返回 `cover_path`、`description`、`availability`。前端还使用旧评分端点和五颗星结构，而真实后端使用条目标签关系与 1 至 10 分。`frontend/src/config.ts` 当前仍设置 `USE_MOCK = true`。

成员六报告记录了在工作副本中重写类型、客户端、组件和视图，但该改动没有进入当前主线。博客和测试结论只能把它记为“待合入并复测”。

这些问题会形成“开发界面看似正常、接入真实接口后数据缺失”的假通过，必须关闭 Mock 后完成真实主链路验收。

### ALPHA-06 Entry 整体评价

数据库与服务中已经存在部分评价和生命周期基础，但 `EntryCreate`、`EntryUpdate` 和 `EntryRead` 尚未暴露 `review` 与 `lifecycle_state`。条目整体评价无法通过真实 API 保存和读取。

## 7. 性能基线

成员四使用一万条目和一万九千条标签关系测试：

| 查询 | 耗时 | 计数耗时 |
|---|---:|---:|
| 首屏无筛选 | 5.5 ms | 1.5 ms |
| 关键词 | 2.9 ms | 1.5 ms |
| 单标签 | 4.1 ms | 2.6 ms |
| 双标签 OR + 评分区间 + 评分排序 | 8.7 ms | 5.5 ms |

当前规模不需要引入 FTS5。中文短片段与 SQLite 内置分词器的限制使 FTS5 不具备直接收益，十万条目阶段再评估倒排索引或 trigram。

分享包小型合成示例的只读预览基线为：单条目 752 字节，平均 7.41 ms；10 条目 1271 字节，平均 8.97 ms。测试不包含封面、原始媒体、真实磁盘读写或低性能设备，不能外推到大型分享包。

## 8. 软工原理与方法

### 契约先行

接口字段、错误码、评分范围和适配器接口先形成书面契约，再由前后端并行实现。当前出现的前后端字段不一致说明契约只有写入还不够，还需要真实接口联调作为验收门。

### 单一职责与关注点分离

条目服务负责业务编排，仓储负责数据访问，适配器负责识别与元数据，桥接层负责原生能力，发布模块负责打包。职责边界让各模块可以独立测试和替换。

### 开闭原则与策略模式

新增文件格式通过实现适配器并注册进入系统，核心分发逻辑无需改写。当前重复注册缺陷说明扩展点本身也必须纳入自动化测试。

### 最小权限与防御性编程

前端不传物理路径，只传 `resource_id`。后端重新验证路径、文件类型和可访问性。危险可执行文件必须先经过用户确认。

### 测试分层与证据等级

领域、应用、API、数据库、端到端和发布测试覆盖不同风险。自动化通过、手工记录和未执行必须分开报告，不能用 Mock 界面或单台安装结果替代完整验收。

### 幂等性与边界值

条目标签关系使用幂等更新，评分边界覆盖 `null`、1、10、0、11、9.5 和布尔值。边界测试能发现宽松类型转换和数据库约束冲突。

## 9. Alpha 出口判断

团队已经具备提交阶段测试报告和演示核心模块的条件，但还不能宣称 Alpha 全部场景通过。

建议按以下顺序完成出口：

1. 修复 `FallbackAdapter` 重复注册，移除严格 `xfail`，重跑全部测试。
2. 修复列表路径泄露和 UTC 时间序列化，并增加 HTTP 回归断言。
3. 合入成员六的界面契约修复，关闭 Mock，接入真实标签评分接口并完成浏览器复测。
4. 为 Entry API 接入 `review` 与 `lifecycle_state`。
5. 挂载桌面 `js_api`，完成文件选择、打开和失效资源场景。
6. 补充前端组件测试或端到端测试，至少覆盖主链路。
7. 修复分享包严格整数校验，确认稳定资料库标识，并完成导出、预览与界面联调。
8. 实现正式导入、冲突处理、事务回滚和资源匹配，执行 TC-01 至 TC-05。
9. 执行 TC-06 至 TC-08 手工场景并记录截图或日志。
10. 安装设备数量已达到口径；如后续要求跨版本覆盖，再补一个不同 Windows 版本的安装记录，并检查卸载残留。

完成以上项目后，再更新本报告的最终结论和自动化基线。
