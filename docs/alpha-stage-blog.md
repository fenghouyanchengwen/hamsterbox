# 《仓鼠盒》Alpha 冲刺阶段测试报告与软工实践总结

> 草案状态：成员五材料待补。正式发布前补齐其测试证据，并删除本提示和所有“待补”标记。

## 一、项目与 Alpha 目标

仓鼠盒是一个本地优先的多媒体收藏管理工具。用户可以建立作品条目，关联硬盘中的电子书、图片、音频、视频、游戏和模型，再通过标签、1 至 10 分评分、整体评价和检索整理自己的收藏。

Alpha 阶段的核心目标不是把所有功能一次做完，而是验证一条真实可用的主链路：

```text
建立条目
→ 关联本地资源
→ 创建标签分类和标签
→ 保存标签评分
→ 按关键词和标签检索
→ 打开资源
→ 通过 Windows 桌面程序使用
```

在这一阶段，团队把“功能是否存在”推进到“接口、数据、界面和发布链路能否相互对上”。测试报告因此不仅记录通过数量，也记录哪些功能只有自动化后端证据，哪些只完成了静态检查，哪些尚未执行。

## 六、场景测试

### 场景一：整理一部新作品

典型用户小李在硬盘里保存了一部电影、字幕和封面。他希望在软件里建立一个条目，而不是把三个文件当成三个作品。

操作流程：

1. 新建“电影”类型的条目，填写标题；
2. 依次关联视频、字幕和封面；
3. 查看资源列表和文件状态；
4. 重新检测被外部移动的文件；
5. 将条目移出库，确认磁盘文件仍保留。

自动化结果显示条目创建、修改、查询、资源关联、缺失检测、恢复、解除关联和移出库均通过。后端不会删除用户原始文件。界面侧的完整点击流程仍受真实接口和桌面桥限制。

### 场景二：为作品设置多个标签和评分

用户创建“内容题材”分类，并在其中创建“科幻”“剧情”两个标签。科幻设为 9 分，剧情暂不评分。

测试覆盖：

- 同一分类内标签不能重名，跨分类可以同名；
- 一个条目可以关联多个标签；
- 标签关系可以不评分；
- 评分只接受空值或 1 至 10 的整数；
- 重复写入同一标签关系只更新原记录；
- 删除仍被引用的标签返回 409，不级联删除关系。

后端场景通过。前端仍使用演示数据和旧评分结构，真实界面联调尚未完成。

### 场景三：找回收藏作品

用户在搜索框输入“塞尔达”，然后点击“动作”标签，并按评分排序。

测试覆盖关键词、中文片段、标签 AND/OR、评分区间、排序和分页。输入 `%`、`_` 时按普通字符处理，不会扩大搜索范围；空结果返回 200 和空数组；越界页码不会变成服务错误。

一万条目、一万九千条标签关系下，最重的组合查询为 8.7 ms，当前阶段不需要引入 FTS5。

### 场景四：打开不同格式的资源

用户关联图片、视频、电子书和未知 `.xyz` 文件。系统应识别类型并交给系统默认程序；`.exe`、`.bat` 等危险后缀必须先经过二次确认。

成员七记录六类手工场景正常，但适配器注册表自动化会因为重复注册 `FallbackAdapter` 失败。单次手工操作不能替代注册表完整验收。

### 场景五：在 Windows 上安装

成员八从 GitHub Actions 运行 #28 下载安装程序，在团队 3 台 Windows 11 家庭版 23H2 电脑上完成安装、启动和卸载，后端连接正常。应用版本为 0.1.0。

团队既有测试用例要求 3 台设备，当前设备数量已经达到。三台设备使用相同 Windows 版本，所以安装链路覆盖了多设备环境，但没有覆盖不同 Windows 版本之间的差异。卸载残留仍未单独检查。

## 八、Alpha 出口条件

Alpha 出口条件不是一组永远不变的勾选项。项目刚进入 Alpha 时，团队希望界面完整、主链路通畅；随着截止时间接近和其他课程任务增加，出口条件逐渐收敛为更重要的问题。

本阶段采用的出口条件分为三层。

### 8.1 最低稳定条件

- 已实现的后端模块可以稳定自动化回归；
- 数据迁移不损坏条目、资源、标签和评分；
- 用户原始媒体文件不会被误删；
- 已发现的致命问题完成修复。

这一层基本达到，全量回归为 161 项通过，迁移和文件安全有专项测试。

### 8.2 可演示主链路

- 关闭 Mock 后仍能建立条目、关联资源、设置标签评分和检索；
- 前端字段、评分端点和错误处理与真实后端一致；
- 桌面窗口可以调用原生文件选择和资源打开；
- 适配器注册表不再阻塞。

这一层尚未达到。

### 8.3 完整 Alpha 验收

- 没有高影响未修复缺陷；
- 分享包导出、预览、校验、冲突与跨设备导入有实际结果；
- 图片、视频、电子书完成真实手工场景；
- Windows 安装在 3 台团队设备上通过。

这一层尚未达到。

因此，我们对 Alpha 的判断是：核心后端可以展示和回归，完整产品链路仍不能宣称验收通过。后续工作的重点是解决木桶中最短的几块板，而不是继续扩展新功能。

## 九、习得的软工原理、方法与技能

### 9.1 契约先行与单一事实来源

团队先冻结条目类型、标签评分范围、接口路径和错误码，再并行实现。每个标签关系只保存空值或 1 至 10 的整数，同一标签关系通过 `PUT` 幂等更新。

实际教训是：把契约写进文档只是第一步。前后端仍然必须用真实接口联调，否则类型检查和 Mock 数据都可能制造“看起来正常”的假通过。

### 9.2 单一职责与关注点分离

条目服务负责业务编排，仓储负责数据库，适配器负责文件识别和元数据，桥接层负责原生能力，发布模块负责打包。职责清楚后，各模块可以用不同方式测试。

重构桥接层时，团队把“查库获取路径”“系统默认程序打开”“文件类型解析”拆开，避免让媒体解析侵入仓储层，也避免让前端直接传入任意绝对路径。

### 9.3 开闭原则与策略模式

新增文件格式时，只需要实现适配器并注册，不修改核心分发逻辑。这个设计让后续扩展格式的成本降低。

本阶段也暴露出一个边界：扩展点本身必须测试。多个兜底适配器本来代表不同文件类型，注册表却把它们误判为重复实例，说明“可扩展”不等于“扩展一定正确”。

### 9.4 最小权限与防御性编程

前端不传物理路径，只传 `resource_id`。后端重新校验路径、文件类型和访问权限。危险可执行文件必须经过用户确认，系统调用不能依赖字符串拼接或 `shell=True`。

这样做牺牲了一点调用便利，但把安全边界放在后端，前端无法绕过。

### 9.5 测试 pyramid 与测试分层

领域测试检查类型和边界，应用测试检查事务，仓储测试检查 SQL 和约束，HTTP 测试检查状态码与错误码，端到端测试检查资源失效和恢复，发布测试检查安装和启动。

测试数量多不代表覆盖完整。成员六有类型检查但没有交互测试，成员七有手工场景但注册表自动化失败，成员八虽然完成 3 台设备安装，但三台设备系统版本相同。报告必须区分自动化、手工和未执行，也要说明环境覆盖范围。

### 9.6 迁移兼容性与可重复构建

空库升级通过不代表老库升级通过。真实迁移还要覆盖已有数据、不同 SQLAlchemy 版本、中文 Windows 编码、CI 路径转义和回滚。

成员一在阶段内修复了 10 个问题，其中老库日期类型、configparser 插值、表名错误和标签级联删除都会直接影响数据安全。这类问题只有构造真实环境和边界数据才会暴露。

### 9.7 幂等性、边界值与错误契约

条目标签关系使用同一对 `(entry_id, tag_id)` 作为主键。重复写入不会产生重复数据，清除评分使用空值。评分边界覆盖 `null`、1、10、0、11、9.5 和布尔值。

稳定错误码比错误文案更适合前端判断。用户看到的是提示信息，程序依赖的是 `TAG_IN_USE`、`RATING_OUT_OF_RANGE` 等稳定标识。

### 9.8 CI、可追踪性与工程卫生

CI 在 Windows runner 上执行 Python 语法检查、后端测试和前端构建；每日构建生成 Windows 预览包。Issue、PR、提交和测试报告把需求、实现和证据连接起来。

团队也犯过把 190 个测试临时文件提交进仓库的错误。后来通过清理和 `.gitignore` 修复，说明自动生成文件、临时数据库和构建产物必须有明确边界。

### 9.9 动态出口条件与范围管理

软件工程不是把所有计划功能强行塞进截止日期。随着问题暴露，团队把出口从“界面完整”调整为“稳定、不崩溃、没有严重缺陷”，再优先处理数据和主链路问题。

动态调整不等于降低所有标准。用户文件不能误删、隐私路径不能泄露、严重缺陷不能隐藏，这些底线不能用截止时间抵消。
