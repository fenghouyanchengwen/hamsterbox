## 1. 测试方法

测试分为三层：

1. 仓储层使用临时迁移库，验证条件组装、排序、计数和标签填充。
2. 接口层使用内存数据库和依赖重写，验证参数校验、错误码和响应结构。
3. 数据量基准使用一万条目和一万九千条关系，测量典型查询耗时。

当前全量基线为 `161 passed, 1 xfailed`，其中检索相关用例 15 个。

## 2. 缺陷

### B1 列表响应泄露本地绝对路径

`GET /api/entries` 的列表项直接沿用 `EntryRead`，因此返回 `cover_path`。该字段是用户磁盘完整路径，与接口契约中“封面路径仅后端使用”的要求冲突。

影响为高，涉及本地目录结构隐私。修复方向是定义独立的列表响应模型，只暴露封面标识或相对引用。

### B2 时间字段缺少时区

UTC 时间经 SQLite 读回后再序列化，响应为 `2026-01-01T08:00:00`，不带 `Z` 或 `+00:00`。浏览器会按本地时区解释，导致北京时间显示偏移八小时。

修复方向是在统一响应模型中补齐 UTC 时区，并确认数据库时间字段的约定。

### B3 前后端字段名不一致

前端使用 `cover`、`summary`、`exists`，后端返回 `cover_path`、`description`、`availability`。关闭 Mock 后，封面、简介和资源缺失标记将无法正确显示。

该问题属于真实接口联调阻塞项，需要前端、条目资源和检索负责人共同确认。

### B4 评分范围存在两套口径

契约、数据库和接口使用 1 至 10 分；部分旧文档和前端注释仍写 1 至 5 分。当前分支已将主要文档统一为 1 至 10 分，真实前端类型仍待联调修改。

### B5 列表响应携带 `share_id`

列表返回 `share_id`，前端类型未使用。是否保留需要接口负责人评审，当前严重程度低。

## 3. 用户场景

| 场景 | 结果 | 证据 |
|---|---|---|
| 输入“塞尔达”找回作品 | 通过 | 标题和简介均可匹配中文片段 |
| 按“动作”标签筛选并按评分降序 | 通过 | 9 分排在 5 分前，未评分排最后 |
| 搜索不存在的关键词 | 通过 | 返回 200、空数组和总数 0 |
| 非法排序、越界页码 | 通过 | 固定错误结构或正常空页 |
| 输入 `%`、`_` | 通过 | 按字面字符处理，不扩大结果集 |

## 4. 性能基线

测试规模为一万条目和一万九千条标签关系。

| 查询 | 耗时 | 计数耗时 |
|---|---:|---:|
| 首屏无筛选 | 5.5 ms | 1.5 ms |
| 关键词 | 2.9 ms | 1.5 ms |
| 单标签 | 4.1 ms | 2.6 ms |
| 双标签 OR + 评分区间 + 评分排序 | 8.7 ms | 5.5 ms |

当前 Alpha 和 Beta 目标规模不需要 FTS5。SQLite `unicode61` 不切分中文，`trigram` 要求查询至少三个字符，均不适合当前短中文片段。

## 5. 结论与后续

后端检索模块功能与性能达到阶段目标。B1、B2 和 B3 分别阻断隐私安全、时间正确性和真实前后端联调，必须在 Alpha 出口前处理。

后续工作包括修复列表响应字段、统一 UTC 序列化、关闭 Mock 并接入真实接口，以及统一评分口径。
