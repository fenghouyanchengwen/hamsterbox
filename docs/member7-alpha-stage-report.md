## 1. Alpha 第一阶段问题

### CI 与本地编码不一致

本地 Windows 测试通过后，GitHub Actions 因默认编码不一致，在写入中文测试文件时抛出 `UnicodeEncodeError`。测试代码已显式指定 UTF-8，并补充媒体测试依赖。

### 跨平台系统 API

早期实现直接调用 Windows 专属 `os.startfile()`，导致静态检查告警和非 Windows 环境失败。Alpha 第二阶段改用统一的 `SystemDefaultOpener`，由资源服务承担路径解析和安全调用。

### Mock 路径依赖

第一阶段的 `_resolve_path` 使用固定假路径，桥接层无法打开真实用户文件。第二阶段已按成员二的资源服务接口改为解析真实资源记录。

## 2. Alpha 第二阶段问题

### 大型或损坏媒体解析可能阻塞

`read_metadata` 虽然有异常捕获，但几十 GB 的损坏视频或压缩包仍可能使底层 `pymediainfo` 长时间运行，导致界面暂时无响应。当前尚未修复，计划增加文件大小阈值或异步解析。

### 不规范的 EPUB 可能没有页数

如果 EPUB 没有内嵌分页标记，`book.pages` 为空，界面无法显示页数。当前通过 `parse_status` 安全降级，不强制输出页数。

### 依赖库打包风险

`pymediainfo` 依赖外部 MediaInfo 库。本地环境已跑通，但干净电脑上的安装包可能缺少底层库，导致视频元数据解析失效。该风险需要和成员八在打包脚本中显式处理。

## 4. 自动化证据差异

成员七的手工记录显示适配场景正常，但当前全量测试中的 `test_built_in_registry_routes_alpha2_file_types` 仍为严格 `xfail`。使用 `--runxfail` 执行会因重复注册 `FallbackAdapter` 失败。

因此：

- 不能据此宣称注册表已通过自动化验收；
- 成员七记录的单个适配器解析结果可作为模块场景证据；
- 修复注册表后必须重跑图片、视频和电子书类型路由测试。

## 5. 软工知识

- 开闭原则与策略模式：新增文件格式只增加适配器并注册，不修改核心分发逻辑；
- 单一职责原则：适配器负责识别和元数据，桥接层负责原生能力，资源服务负责查库和安全边界；
- 最小权限原则：前端只传 `resource_id`，不传物理路径；危险可执行文件必须二次确认；
- 契约先行：先冻结 `EntryType`、适配器接口和跨成员调用方式，再并行实现。

## 6. 结论

适配器业务场景已有手工证据，但自动化注册表失败仍阻止 Alpha 模块完整验收。后续需要修复重复注册问题、重跑冒烟测试，并在干净 Windows 环境验证安装包内的媒体依赖。
