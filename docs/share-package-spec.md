# HamsterBox Share Package Format

Purpose: Define a portable, versioned format for sharing entry metadata and evaluations between HamsterBox libraries.

Owner: Member 5 (Share Package)

Last updated: 2026-10-30

Status: Draft for review with the shared T02 domain model. Field names and stable identifier storage must be confirmed before this format is frozen.

## 1. Goals and boundaries

A share package lets a recipient preview and selectively import entries, tags, ratings, reviews, and optional cover images. It does not transfer original media or executable files. Import never writes to the database until the recipient confirms the preview; the final write is atomic.

The package contains no absolute local paths, local database primary keys, credentials, API keys, or machine-specific settings. Resource identity is represented by a SHA-256 fingerprint and safe display metadata. A resource's filename is informational only and must not be treated as proof that two files are the same.

The format supports repeatable imports, schema validation, corruption detection, and future compatible extensions.

## 2. Archive layout

The proposed file extension is `.hbox`. A package is a ZIP archive with this layout:

```text
<name>.hbox
├── manifest.json
└── covers/
    └── <sha256>.<extension>
```

`manifest.json` is required and encoded as UTF-8 without a byte-order mark. Cover files are optional. No resource media files may be included. Cover images are the only binary assets allowed in v1; a cover must be an image associated with an entry, not an original resource file.

The archive paths are generated by the exporter. Import rejects absolute paths, `..` path segments, backslashes, NUL bytes, duplicate archive paths, encrypted members, and symbolic links. The importer validates the ZIP central directory and each member's declared and actual size before reading it. Proposed initial ceilings are 50 MiB for the full archive, 10 MiB for `manifest.json`, and 5 MiB per cover; confirm these with T02 before freezing v1.

## 3. Manifest v1

The following is the proposed top-level shape:

```json
{
  "format": "hamsterbox-share-package",
  "format_version": "1.0.0",
  "generated_by": {
    "name": "HamsterBox",
    "version": "0.1.0"
  },
  "package_id": "f7fd246b-d550-4dd5-97b2-91bb54b75f3f",
  "source_library_id": "3ddadfd0-b2a4-4a56-9b08-148b332af6d4",
  "created_at": "2026-10-30T18:30:00Z",
  "entries": []
}
```

Required top-level fields:

| Field | Type | Meaning |
| --- | --- | --- |
| `format` | string | Constant `hamsterbox-share-package`. |
| `format_version` | string | Semantic version of the package schema. V1 starts at `1.0.0`. |
| `generated_by.name` | string | Exporting application name. |
| `generated_by.version` | string | Exporting application version. |
| `package_id` | UUID string | Unique identifier for this exported package. |
| `source_library_id` | UUID string | Stable, random identifier for the originating library; enables repeat imports to be recognized without exposing a path or account identity. |
| `created_at` | UTC timestamp | Package creation time, ISO 8601 with `Z` suffix. |
| `entries` | array | Entries selected for export; an empty array is invalid. |

`source_library_id` and the per-entry/per-tag share identifiers must be stable across repeated exports. They are portable identifiers, not SQLite primary keys. The shared T02 model must provide or approve these identifiers before v1 is frozen.

### 3.1 Entry object

Each entry has this proposed shape:

```json
{
  "share_id": "a19d1060-7288-4c86-a2e7-3340c7c58be1",
  "title": "示例作品 A",
  "type": "game",
  "description": "示例简介",
  "created_at": "2026-10-29T08:00:00Z",
  "updated_at": "2026-10-30T09:15:00Z",
  "resources": [],
  "tags": [],
  "entry_tags": [],
  "cover": null
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `share_id` | UUID string | Stable portable identifier for this entry within its source library. |
| `title` | string | Required, non-empty display title. |
| `type` | string | Entry type from the shared domain model; v1 must not invent a separate enumeration. |
| `description` | string or null | Optional user-authored description. |
| `created_at` | UTC timestamp | Original entry creation time. |
| `updated_at` | UTC timestamp | Last entry metadata update time. |
| `resources` | array | Resource fingerprints and safe display metadata, never local paths or file contents. |
| `tags` | array | Tag definitions needed by this entry's tag associations. |
| `entry_tags` | array | Per-entry tag association, optional rating, and review. |
| `cover` | object or null | Optional reference to an embedded cover image. |

`type`, timestamps, and description should be mapped to the agreed Entry fields from T02. Unknown application-only fields are not exported in v1 unless explicitly added to this specification.

### 3.2 Resource object

```json
{
  "share_id": "c73ef2e8-dcf8-4d3b-8e44-36cd95c1e4d8",
  "file_name": "sample_game.exe",
  "extension": ".exe",
  "size_bytes": 123456,
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "availability_at_export": "present"
}
```

- `share_id` is a stable UUID for portable references; it is not a local resource primary key.
- `file_name` is a basename only. `/`, `\\`, drive prefixes, and parent-directory segments are invalid.
- `extension` is informational and normalized to lowercase with a leading dot, or an empty string when unknown.
- `size_bytes` is a non-negative integer or null.
- `sha256` is 64 lowercase hexadecimal characters when known, otherwise null.
- `availability_at_export` is `present` or `missing`. If `missing`, the hash may be null; a missing path is never serialized.

The exporter computes SHA-256 from the original file when it is readable. It records a missing or unreadable resource without blocking metadata export, and reports that condition to the user. The importer matches only on SHA-256. A filename match by itself never creates an automatic association.

### 3.3 Tag and entry-tag objects

Tag definition:

```json
{
  "share_id": "af98d02a-2016-4efd-ad47-2f74a75dab0f",
  "name": "剧情",
  "color": "#5B8DEF",
  "rating_enabled": true
}
```

Entry-tag association:

```json
{
  "tag_share_id": "af98d02a-2016-4efd-ad47-2f74a75dab0f",
  "rating": 5,
  "review": "示例评价"
}
```

`rating` is an integer from 1 through 5 or null. `review` is a string or null. A tag can be present without a rating; the review and rating belong to the entry-tag association, not to the global tag definition. Names are not unique identifiers; two tags with the same name may remain distinct if they have different share IDs.

### 3.4 Cover object

```json
{
  "archive_path": "covers/aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa.png",
  "media_type": "image/png",
  "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "size_bytes": 2048
}
```

The path must be under `covers/` and must match an actual ZIP member. The digest and size are checked before import. Covers are optional; absence or invalid cover data must not invalidate otherwise valid entry metadata. The importer must never interpret `archive_path` as a filesystem path outside the archive.

## 4. Import preview and conflict model

Import status is local preview data and is not written into the shared manifest. For each selected entry and resource, the preview reports one of these states:

| State | Meaning | Default action |
| --- | --- | --- |
| `auto_linked` | Exactly one local file has the same SHA-256. | Offer that file as the proposed association. |
| `needs_selection` | More than one local file has the same SHA-256, or the user must choose an association. | Ask the user to select one or leave unlinked. |
| `missing` | No local file matches the provided hash, or the source marked the resource missing. | Import metadata without a local resource association. |
| `conflict` | Same-origin entry already exists with differing data, or a same-name candidate has a different hash. | Explain the mismatch and let the user skip, keep both, or explicitly replace supported metadata. |

The preview must support selecting a subset of entries. No database writes occur during archive parsing, validation, or preview. On confirmation, all selected records are committed in one transaction; if any write fails, the transaction is rolled back.

Repeated import of the same source entry is detected by `(source_library_id, entry.share_id)`. It must not silently create uncontrolled duplicates. Conflicting updates are shown in preview and require an explicit user choice. Hash matches use SHA-256, never a filename-only shortcut.

## 5. Validation and corruption handling

The importer performs these checks before showing a successful preview:

1. Confirm the file is a readable ZIP archive and contains exactly one root `manifest.json`.
2. Reject unsafe paths, duplicate members, encrypted members, symlinks, unsupported compression, and configured size-limit violations.
3. Parse UTF-8 JSON; reject duplicate JSON object keys and malformed JSON.
4. Validate `format`, supported major version, required fields, UUIDs, timestamps, arrays, and primitive types.
5. Validate every tag reference and every cover reference; verify cover size and SHA-256.
6. Validate ratings as integers from 1 to 5 or null, resource hashes as 64 hexadecimal characters or null, and file names as basenames.
7. Reject duplicate `share_id` values where uniqueness is required and reject an empty `entries` array.

Any validation failure rejects the package before database mutation. A package must never be partially imported because one member is corrupt. Error results should include a stable error code and a human-readable message without exposing local paths.

## 6. Version compatibility

- A new exporter writes `format_version: "1.0.0"` for this initial schema.
- A v1 importer accepts major version `1`, validates all required fields, and ignores unknown optional fields so additive minor updates remain readable.
- A v1 importer rejects an unknown major version with an unsupported-version error before any database change.
- Any change to required-field meaning, identifier semantics, rating range, or archive layout requires a major version increment.
- New optional fields may be added within major version 1 only when older importers can safely ignore them.
- `generated_by.version` is informational and does not determine schema compatibility.

## 7. Decisions required before freezing v1

The following must be confirmed with the shared T02 contract and relevant owners:

- Whether Entry, Resource, and Tag records persist stable UUIDs for `share_id` values, and how `source_library_id` is created and stored.
- Exact Entry and Tag field names/types, nullability, and timestamp availability.
- Whether covers are embedded in the package or referenced only; this draft proposes embedded cover images with strict limits.
- Archive and manifest size ceilings.
- Which conflict choices are supported in the first importer and whether “replace metadata” is in scope.
- How imported tags with matching names but different share IDs are presented to the user.

After agreement, remove this draft status, freeze the JSON Schema, and add a reproducible sample `.hbox` fixture for validation and import tests.
