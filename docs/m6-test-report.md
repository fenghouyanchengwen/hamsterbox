## 二、Bug List（v0.2.0）

### B1　开发服务器只绑 IPv6，按文档访问 `127.0.0.1` 打不开

- **现象**：`npm run dev` 后 Vite 打印 `Local: http://localhost:5173/`，按其提示访问正常；但项目文档、代理和桌面窗口用的都是 `127.0.0.1`，打开 `http://127.0.0.1:5173` 报"无法连接到远程服务器"。
- **验证方式**：分别用旧写法与新配置启动开发服务器，查实际监听地址并对两个主机名各发一次请求。

  | 配置 | 实际监听 | `localhost:5173` | `127.0.0.1:5173` |
  |---|---|---|---|
  | 默认不写 `host`（原状） | `::1` | HTTP 200 | **连接失败** |
  | `host: '127.0.0.1'`（现配置） | `127.0.0.1` | HTTP 200 | HTTP 200 |

- **影响**：高。照着文档操作必失败，且现象是浏览器级"连不上"，新手很难联想到 IPv6。
- **原因**：本机 `localhost` 解析顺序为 `::1` → `127.0.0.1`；Vite 默认 `host: 'localhost'`，Node 监听时只取解析结果的第一个地址，于是只绑 IPv6 回环。
- **附带风险**：`localhost:5173` 与 `127.0.0.1:5173` 属于两个不同 origin，`localStorage`、缓存互不相通；桌面版 `127.0.0.1:8000` 又是第三个。当前未使用存储所以无感，接设置页后会表现为"设置丢失"。
- **状态**：已修复。`vite.config.ts` 显式 `host: '127.0.0.1'`，并开启 `strictPort: true`（端口占用时直接报错，不再静默换 5174）。已在 `docs/frontend-guide.md` 补"统一用 127.0.0.1"一节，防止后人删掉该行。
- **归属**：成员六。

### B2　前端类型与后端契约整体不一致

- **现象**：前端使用 `cover`、`summary`、`exists`，后端返回 `cover_path`、`description`、`availability`；评分路径用 `/entries/{id}/ratings/{tag_id}`，实际为 `/entries/{id}/tags/{tag_id}`；标签是单层 `Tag{color, rating_enabled}`，后端是「分类 → 标签」两级；评分范围前端 1–5，后端 1–10。
- **依据**：`docs/api/entries-resources.md`、`docs/tag-rating-contract.md`（2026-11-01 冻结）。
- **影响**：高。关闭 Mock 后卡片无封面无简介、缺失标记失效、评分写入 404，属联调阻塞项。成员四的测试报告已作为 B3 记录同一问题。
- **原因**：前端骨架写于 10 月 31 日，后端在 11 月 2 日与 11 月 7 日两次冻结契约，未同步。
- **状态**：已修复（T6-01，2026-11-09）。类型、客户端、演示数据、桥封装、组件与视图全部按新契约重写，`vue-tsc` 与 `vite build` 均通过。**代码仍在 `feature/ui-whole-interact` 分支未提交**。
- **归属**：成员六；`EntryRead` 的对外字段需成员二确认。

### B3　评分口径 1 至 5 与 1 至 10 并存

- **现象**：契约、数据库约束、接口校验均为 1 至 10，前端源码已改为 1 至 10（`RATING_MIN` / `RATING_MAX` 常量、`RatingScale` 十档控件）。
- **验证方式**：全仓检索"1 至 5""1-5 分""五颗星"。
- **结果**：源码 0 处。残留仅出现在迁移脚本的降级注释（`0002_tag_category_review.py`）和"已从 1 至 5 改为 1 至 10"的说明性文字中，属历史说明，不影响行为。
- **影响**：低。前端已无实际冲突，风险在文档口径。
- **状态**：前端已修复；文档口径统一仍待处理（对应成员四报告的 B4）。
- **归属**：成员六已改代码，文档由成员三、成员四收口。

### B4　桌面版加载的是陈旧构建产物

- **现象**：`frontend/dist` 为 2026-11-02 生成，而源码在 2026-11-09 之后又有多轮改动。旧包内的条目类型仍是中文（`电子书` 等），字段仍是 `summary`，且不含 `availability`、`cover_path`。
- **实际后果（2026-11-25 实测）**：在桌面版新建条目返回 `422 VALIDATION_ERROR`。后端 `details.errors` 指明 `loc: ["body","type"]`、`input: "电子书"`，而契约只接受 `game`/`book`/`video`/`audio`/`image`/`model`/`other`。**后端行为正确，是旧构建产物在发过期载荷。**
- **影响**：中高。`python desktop/launcher.py` 打开的是六天前的界面，演示或验收会看到与源码完全不符的页面，并伴随接口 422。
- **原因**：`dist` 不进版本库，也没有任何机制提示它已过期。
- **状态**：已缓解（2026-11-25 重新构建，新产物 `index-BYR6vCei.js`，包内已无中文类型与 `summary`）。**流程风险仍在**：没有机制阻止下次再犯。
- **归属**：成员六（重新构建）+ 成员八（在启动脚本或 README 里加产物过期提示）。

### B5　桌面桥未挂载，原生能力在桌面版全部不可用

- **影响**：高。选文件、打开资源、定位文件、另存为全部不工作，"关联本地文件"这条主链在桌面版断开。
- **状态**：未修复，前后端两侧各缺一块。前端已按真实返回结构 `{ok, error}` 封装并写好退化分支，待后端接通即可生效。
- **归属**：成员八（挂载 `js_api`）+ 成员七/二（路径解析实现）。

### B6　列表接口缺失，列表页只能跑演示数据

- **现象**：`package.json` 无 vitest / playwright / jest / cypress，回归全靠手工点击。
- **影响**：中。本轮契约对齐涉及 15 个文件，只能靠类型检查兜底，行为回归无法自动发现。

### B8　列表卡片不显示标签，存在 N+1 隐患

- **现象**：条目卡片只有标题、类型、简介、更新时间，没有标签。
- **原因**：列表接口未定义是否返回标签摘要；若逐条请求 `/entries/{id}/tags`，20 张卡片会产生 20 个请求。
- **影响**：低（信息缺失），但决策错误会带来性能问题。
- **状态**：已记录，待成员四确认后决定是"接口带摘要"还是"卡片不显示标签"。
- **归属**：成员六 + 成员四。

### B9　响应中的 `cover_path` 泄露本地绝对路径

- **现象**：`EntryRead` 返回 `cover_path`，值为用户磁盘完整路径。
- **依据**：`docs/tag-rating-contract.md` §3.1 要求该字段仅后端使用，不在响应中泄露。
- **影响**：中（隐私）。与成员四报告的 B1 为同一问题。
- **前端处置**：已不使用该字段渲染封面（本地路径在 http 页面里本就加载不了），卡片改用首字渐变占位，未扩大暴露面。
- **状态**：后端未修复。前端已规避。
- **归属**：成员二、成员四。

### B10　422 只显示"请求字段校验失败"，看不到具体字段

- **现象**：新建条目校验失败时，界面只有一句「请求字段校验失败（VALIDATION_ERROR）」，用户与开发者都无法判断是哪个字段错了。
- **依据**：后端 `validation_error_handler` 已把 Pydantic 的原始错误放进 `details.errors`（形如 `[{loc: ["body","type"], msg: "...", input: "..."}]`），信息是有的，前端没展示。
- **影响**：中。这正是 B4 被误判成"后端有问题"的直接原因——提示里看不出是 `type` 收到中文值。
- **状态**：已修复（2026-11-25）。`utils/error.ts` 新增 `validationDetail()`，422 时把字段名、原因与收到的值一并显示，例如「字段 type：Input should be 'game', 'book'…，收到 "电子书"」。
- **归属**：成员六。

## 四、性能基线

| 指标 | 实测 |
|---|---|
| 构建模块数 | 51 |

| 产物 CSS | 11.50 kB（gzip 2.67 kB） |

## 五、Alpha 出口条件

从前端模块出发，本阶段的最低出口是：

1. 三栏界面在浏览器（5173）与桌面窗口两处都能正常加载；
2. 列表、详情、资源三处的四种状态（加载中、空、错误、有数据）齐全，错误态有可执行的重试；
3. 移出库文案明确"不删除磁盘文件"，且需二次确认；
4. 评分可写 1 至 10 分，`null` 表示未评分；
5. 条目类型以中文展示，提交英文枚举；
6. 关闭 `USE_MOCK` 后主链路可用：建条目 → 挂文件 → 打标签评分 → 检索。

当前第 1、6 两条不满足：桌面窗口因 B4（产物陈旧）与 B5（桥未挂载）未验证；第 6 条因 B6（列表接口缺失）无法执行。其余四条已满足，B2 更是在本轮修掉了最大的联调阻塞。

已知限制：

- 无自动化测试，行为回归只能手工覆盖；本轮契约对齐涉及 15 个文件，仅靠类型检查兜底。
- 列表未接真接口，演示数据与真实数据形态可能仍有差异，联调时需整体复测一遍。
- 封面不显示：`cover_path` 是本地绝对路径，在 http 页面里无法作为图片来源，且契约要求不外泄；卡片暂用首字渐变占位。
- 桌面能力（选文件、打开资源）只能在 `npm run build` 后用桌面窗口验证，浏览器里始终走退化分支。
- 未引入组件库，按钮与输入框是手写 CSS，交互细节（焦点环、禁用态）只能逐个补齐。
